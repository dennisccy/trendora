# Project story so far

Trendora ranks stocks with explainable, evidence-checked signals. This chapter tracks making the running app itself trustworthy day to day — fast, honest about its own state, and resilient under heavy background work.

## How it has grown

Early rounds removed a hidden backfill limit, moved slow calculations to run once at ingest, added a live status badge, and fixed a cluster of low-memory crashes, cutting one calculation's peak memory from 7.8 GB to 3.1 GB. Iterations 51-57 fixed a sometimes-silent status light, sped up two slow pages, and stopped a busy data-fetch job from wrongly claiming there was no data. Iteration 58 fixed a wrong health-check record but left two journeys open, and the team returned to its full review process after some test write-ups stopped matching their raw measurements.

Iteration 59 delivered the project's best engineering yet on those two open journeys: the Regime Lab page can no longer crash under memory pressure — the one part that can't finish shows an honest "temporarily unavailable" note instead — and a real kill-and-restart test proved the Data page still shows correct saved numbers in under a second. Iteration 60 finished the small pieces from the round before and had the app's best day yet, finishing an 18-minute data job with zero errors — but it also mis-read a Data page number as stale, comparing a screenshot to a database entry using two different clocks, and held a journey back on that mistake.

Iteration 61 caught and corrected that mistake: the database stores its times in one timezone, and the app's own logs and screenshots use another, an hour apart — once accounted for, the Data page number was right all along. With that cleared up, the "aggregates are precomputed at ingest" journey moved to passing: seven of the product's eight promises now work. The round also shipped a real improvement — the Data Manager page began refreshing its own numbers automatically about every 30 seconds, so a colleague's or script's backfill shows up without a manual reload.

Iteration 62 shipped two more small, verified fixes: the app's own health-check report now states its real latest scan date instead of a placeholder, and the Data Manager page stopped erasing your numbers off the screen if one of its automatic background checks happens to fail — it now just waits quietly for the next one to succeed. No journey changed status this round, but the round's automatic checking tools ran a real end-to-end test of the "precomputed at ingest" promise for the first time, including a genuine 15-minute background data job that finished cleanly. That same testing round also turned up two glitches in the checking tools themselves — one that can cry wolf if it starts checking too soon after a restart, and a rehearsal run that used up the one practice date it needs kept empty — which the team now plans to fix before anything else. The last open promise, keeping the app responsive during very heavy background jobs, still waits on one sentence from the product's owner: how fast must the app answer while a very long job is running in the background? That question has now been asked for 14 rounds running, though the team has also found a concrete way it might close the gap on its own by speeding up the slowest part of that background job.

## What it can do today

The product lets users browse stock rankings, sector and theme views, backtests, and all five research tools with an honest "starting up"/"backend unavailable" status. It accepts a backfill over any date range with no hidden cap, explains clearly when there's nothing new to fetch, serves backtest results instantly from storage, and discloses when it's crunching numbers in the background. Pages load quickly because they only fetch what they need. The Data Manager page keeps its snapshot and gap counts current on its own, refreshing automatically within about 30 seconds of any backfill finishing — even one started elsewhere — and no longer wipes those numbers off the screen if a single automatic refresh check happens to fail. The Regime Lab page keeps working under heavy server load, showing a plain "Unavailable" notice instead of a misleading zero for any part it can't calculate in the moment. The app's own health report now tells the truth about the latest scan date rather than a placeholder.
