# Project story so far

Trendora ranks stocks with explainable, evidence-checked signals. This chapter tracks making the running app itself trustworthy day to day — fast, honest about its own state, and resilient under heavy background work.

## How it has grown

Early rounds removed a hidden backfill limit, moved slow calculations to run once at ingest, added a live status badge, fixed a cluster of low-memory crashes, and brought seven of the product's eight core promises to passing after fixing a timezone mix-up. A multi-round hunt for slow health-check replies during heavy background jobs (iterations 62-71) ended with two root causes found and fixed: the app now pre-computes its status answer instead of recalculating it live, and a database connection-pool shortage that once caused a two-and-a-half-minute silent gap was closed.

Iteration 72 resized that connection pool with a boot-time safety check and made the status check always answer instantly from a cached value — but raised a new question: how much memory the app now uses with more than twice as many database connections open, on a machine with a history of memory crashes. Iteration 73 tried four times to measure that and could not finish, each attempt interrupted; the team recorded a partial reading rather than guess. Iteration 74 finally succeeded on the first try: during a real, heavy background job the app's memory use peaked at 4,724 MB of its 8,192 MB allowance — 42% to spare — while still answering every status check on time. That confirmed the eighth and final core promise, though two smaller promises (backtest storage, background-activity disclosure) were still resting on two-round-old proof, because the automated screenshot tool kept serving broken, unstyled pages instead of real evidence.

Iteration 75 set out to repair that screenshot tool and re-check those two promises properly. The tool behaved itself this round — every screenshot came back as the real, fully-drawn app, none of the broken pages that had spoiled the previous three rounds — so the team re-verified the backtest-storage and background-activity promises with fresh, first-party proof for the first time since iteration 72. But the actual repair job was skipped: no developer worked this round, so the glitch behind the broken screenshots is still undiagnosed, just quiet for now. All eight core promises are confirmed passing today; what remains is finding that root cause, tightening a couple of the automatic checks so they'd actually catch a real problem, and a batch of small self-review housekeeping notes the team is now asking the project owner how strictly to treat.

## What it can do today

The product lets users browse stock rankings, sector and theme views, backtests, and all five research tools, always with an honest status message while the backend starts up. Backfills accept any date range with no hidden cap and explain when there's nothing new to fetch. Freshly calculated aggregates are ready right after a data import rather than computed on the fly, backtest results load instantly from storage with a "refreshing" note while new numbers compute, pages fetch only what they need, and the app discloses when it's crunching numbers in the background and when it's done. All eight core promises are confirmed working, most recently reconfirmed with fresh proof this round.
