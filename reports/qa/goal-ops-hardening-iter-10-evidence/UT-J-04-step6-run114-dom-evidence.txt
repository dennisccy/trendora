--------------------------------------------------------------------------------------------
WHAT THIS SHOWS
--------------------------------------------------------------------------------------------

- Status badge (data-testid="run-status"): "interrupted" — NOT a stuck "running" row.
- Snapshots column: 59 (non-zero) — this is the exact field that was "0" for every
  pre-fix interrupted row (see contrast below).
- Breakdown (data-testid="backfill-breakdown"): "120 calendar days . 5 already
  snapshotted . 36 non-trading" — non-null, real values (not "—"/blank).
- Summary message: "backfill: 59 snapshots over 84 dates, 136380 forward returns" — a real,
  specific persisted message, not a generic placeholder.
- Arithmetic check (TC-2): non_trading_days(36) + dates_total(84) = 120 = calendar_days. OK.
  snapshots_created(59) + already_snapshotted(5) + error_other(0) = 64. This does NOT equal
  dates_total (84) — but it DOES equal dates_done (64, per the API's GET /api/data record for
  this same run id 114), because this run was INTERRUPTED partway through (64 of the planned
  84 target dates had actually been processed at the moment of the kill; the remaining 20 were
  never reached). TC-2's formula as literally written assumes a completed run; for an
  interrupted run the correct invariant is against dates_done, not dates_total, and that
  invariant holds. This is the expected, honest behavior of a partial-progress checkpoint, not
  a defect — it is the SAME distinction the current backend already draws between dates_done
  and dates_total, just not separately re-labeled as its own number in this historical-row
  view (dates_done is shown live only in the still-running Job Progress panel, per
  apps/frontend/app/data/page.tsx:2763; the completed/interrupted Run History row instead shows
  the derived breakdown fields, which are correct and non-null here).
