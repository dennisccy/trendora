GET /api/health -- 8 consecutive polls at 2s timeout each all failed with no response (16s+
total unresponsiveness observed). Process memory at that point (/proc/<pid>/status):

This VmSize-pinned-exactly-at-the-ulimit-v-ceiling signature, with VmRSS well below it, is the
classic fingerprint of virtual-address-space exhaustion rather than physical-memory exhaustion.

=== Scope check (same boot as reproduction #2's successor process, 2887992) ===

=== Config evidence (config.yaml) feeding the working hypothesis ===
database:
  pragmas:
    mmap_size_bytes: 1073741824   # 1 GB read-mmap window -- NEW this iteration (item B)
  pool_size: 10                   # NEW this iteration (item B)
  max_overflow: 20                # NEW this iteration (item B)
server:
  memory_cap_mb: 6144   # ulimit -v cap; comment says it was sized for "the one-copy ~3.27M-row
                         # bar prefill ... retained footprint ~0.4-0.5 GB" -- i.e. calibrated only
                         # for the Python-heap prefill cache, with no apparent accounting for the
                         # NEW per-connection mmap window x pool_size/max_overflow added by the
                         # same iteration's item B.

Working hypothesis (inference from the above, not confirmed by a controlled ablation test):
item B's new mmap_size_bytes (1 GB) x pool_size/max_overflow (up to 30 pooled sqlite connections)
can inflate the process's virtual address space well past the pre-existing memory_cap_mb (6144 MB)
ulimit -v ceiling -- a ceiling whose own docstring reasoning does not mention the new mmap window.
Whether this reproduces on every cold boot or only when combined with concurrent system memory
pressure was not established with certainty; it reproduced on 2 of 2 attempts in this session.
