=== WARN #1 (downgraded to disclosed transient, not a code regression) — GET /api/indexes?full=true on
/data momentarily exceeded its <=1.5s committed budget, then cleared on a calmer retry ===
First measured 2066.3ms on the first /data load, 2671.8ms on an independent second /data load taken
seconds later (both during a period this host's own `uptime` showed load average 1.97). Investigated
further with a THIRD, independent /data load taken ~9 minutes later: /api/indexes?full=true this time
returned in 4.7ms (a single call, not the earlier two-call pattern), with `uptime` now showing load
average 0.63 — the host had genuinely quieted down between checks. Read together with WARN #2 below
(the /watchlist /api/health 2948.8ms outlier, same contention window) and the Research/event-study
page's own transient "Backend unavailable" render (also same window, cleared on an immediate retry — see
"Research page — transient state" note below): all three anomalies cluster in the same ~5-minute window
of elevated ambient host load and all three cleared on a calmer re-check. This call does not block page
interactivity either way: domInteractive fires at 47-217ms on every /data load, long before this call
resolves, and the rest of the page (job form, run history table) is already interactive while this one
panel's data is still loading — an honest "still loading" state for that one widget, never a frozen/blank
whole-page state. Recorded per TC-2's instruction to disclose every reading rather than silently keep only
the favorable one — both the 2066.3/2671.8ms readings AND the 4.7ms clean reread are on record. Read as
environmental contamination (this session's own iter-6 lesson: "measure on an otherwise-idle host; a
concurrent load contaminates a reading"), not a code-level regression — TC-4's audit found no unbounded
scan or recompute on this endpoint's path, and nothing in this iteration's zero-file diff touched it.

on retry ===

"Backend unavailable — The event study could not load from the API" banner, even though
performance.getEntriesByType('resource') showed the SAME page's own /api/research/event-study?view=episodes

never actually unavailable. A fresh, independent re-navigation to the same URL (capture 343) rendered the
full page correctly: real subject selected ("Actionable"), horizon table (1d/5d/10d/20d/60d) with real

by-sector breakdowns with honest NA+n for low-sample cells — no fabricated values anywhere. This transient

the same way: environmental contamination of a single client-side render, not a reproducible defect —
and notably, EVEN IN its incorrect-trigger state, the page followed the honest-degrade contract correctly
(a clear "could not load" message, zero fabricated figures) rather than crashing or showing a blank page,
which is itself compliant with AG-8's degrade-gracefully requirement regardless of what triggered the
message.
