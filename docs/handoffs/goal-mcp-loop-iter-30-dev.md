## What Was Built

J-18 / backlog B-901 — the pre-registration registry + gate cross-check (the governance keystone):

- **`app.engine.registry`** (new, pure): `resolve_registry_path()` (env `TRENDORA_REGISTRY_PATH` override,
  else `config.evidence.registry.path`, mirrors `app.engine.evidence.resolve_ledger_path()` exactly),
  `load_registrations(path=None)` (missing/empty file -> `[]`, never a crash), `claim_selectors(claim)`
  (builds the exact selector-set: `kind` + present `_CLAIM_SELECTOR_KEYS` + `horizon` + `direction`,
  excluding display-routing keys `signal`/`ledger`), and `match_registration(claim, registrations=None)`
  (EXACT dict-equality match only — no fuzzy/superset matching).
- **Backfill** — `runs/goal-session-mcp-loop/state/pre-registrations.jsonl`, 11 rows. Generated by a
  one-off script that calls the real `claim_selectors()` against every entry in both live ledgers
  (`certified-claims.jsonl` + `staging-ledger.jsonl`, 7 + 7 = 14 raw entries) and deduplicates by exact
  selector-set, so every row's `selectors` is guaranteed round-trip-consistent by construction, not by
  hand-transcription. See "Row-count discrepancy" below — this is the one deliberate deviation from the
  spec's literal wording, reasoned through and test-proven.
- **`GET /api/research/registry`** (new, `app/api/registry.py`) — serves `load_registrations()` verbatim
  as `{"registrations": [...]}`. No DB/session; 200 + empty list on a missing file, never 500.
- **Gate teeth** (`project-extensions/gates/verify_claim.py`) — a new pre-check in `main()`'s per-claim
  loop, inserted BEFORE the existing `tools.verify_edge(...)` call: when `evidence.registry.enforce` is
  true and `registry.match_registration(claim)` returns `None`, the claim is appended to `results` as
  `{"status": "BLOCKED", "reason": <names the registry + gives the /research/registry + register path>}`,
  `blocked = True`, and the loop `continue`s — `verify_edge` is never called, no ledger write, no
  Bonferroni-bar tightening. A match, or `enforce=False`, falls through completely unchanged (byte-
  identical pre-iter-30 behavior). No new parameter threads into `verify_edge`/`certify_edge`/the ledger
  modules — the pre-check is a pure short-circuit, exactly as the plan's Critical Implementation Detail
  required.
- **Config** — new `RegistryCfg` (`path: str`, `enforce: bool = False`) in `app/config.py`, added as
  `EvidenceCfg.registry`. `config.yaml` gained `evidence.registry.{path,enforce}` as a sibling block to
  the existing `fdr:` sub-block. `enforce` was landed `false`, the backfill + gate were verified complete
  (backend tests + a live end-to-end smoke run), and ONLY THEN flipped to `true` as the literal last edit
  of this dev pass — the sequencing the plan's Critical Implementation Detail demanded.
- **`run-goal.sh`** (the symlinked framework script, real path
  `incredible_auto_dev/scripts/automation/run-goal.sh`) — `TRENDORA_REGISTRY_PATH` now exported alongside
  `LEDGER_PATH`/`STAGING_LEDGER_PATH` at both dispatch sites (the post-decompose gate call, and the
  post-goal continuous-improvement hook call), so the gate always resolves the same file the endpoint
  serves.
- **`/research/registry`** (new page) — a read-only table (selectors as key=value chips, rationale,
  registration date, source, status) reading only `GET /api/research/registry`. Backfilled rows carry a
  visible "backfill" pill. Status renders in the Badge `default` (neutral/muted) variant deliberately —
  NOT the accent/danger PASS/FAIL coloring `/evidence` uses — so "tested"/"closed" (a descriptive process
  state) is never mistaken for a proven/not-proven signal. Loading skeleton, fetch-error card, and an
  honest empty state (should not occur post-backfill, but the page degrades gracefully rather than crash
  if the file is ever absent). No forms, no edit/delete affordance anywhere.
- **Research hub** — a new "Governance & process" section below the existing `RESEARCH_LABS` grid, one
  card linking to `/research/registry`. `lib/research-labs.ts`'s `RESEARCH_LABS` array (the ten labs, a

  `app/research/page.tsx` directly, per the plan's Assumption #5 (this establishes the pattern the three

## Known Issues

- **Row-count discrepancy (deliberate, reasoned, test-proven):** the phase spec's DoD says "≥14
  ledger-derived rows"; the committed registry has **11** distinct rows. I enumerated both ledgers: 7
  canonical + 7 staging = 14 raw entries, but 3 pairs are EXACT selector-set duplicates (a staging
  candidate later promoted/re-tested under `"ledger":"canonical"` with the identical cohort selectors:
  `vcp_contraction` d10 h60; `rs_spy_3m` d10 h60; the `rs_spy_3m`+`high_proximity` h20 combination).
  `match_registration` must return ONE row for an exact selector-set (it is a lookup, not a list), so the
  registry cannot hold two rows sharing an identical selector tuple — 14 raw entries dedup to 11. I did
  not hand-count this: `test_registry.py::test_committed_registry_backfill_is_complete_and_deduplicated`
  and the two `..._round_trips_every_..._ledger_claim` tests programmatically verify (a) exactly 11 rows,
  (b) every one of the 14 raw ledger entries across BOTH files matches exactly one backfilled row via the
  real `match_registration` function, and (c) no two rows share a selector-set. Flagging this explicitly
  per the coordinator's instruction so review isn't surprised by 11 vs "≥14" — the completeness +
  exact-match-correctness bar is met; the literal count is not, because the spec's author (the decomposer)
  did not derive the cross-ledger overlap when writing "≥14".
